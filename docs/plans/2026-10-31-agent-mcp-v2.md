# Money MCP v2: an agent that can run the books

Status: **plan, agreed in chat on 2026-10-31. Nothing here is built yet.**
Branch base: `cursor/mcp-writes` (PR #25). Test target: Neon branch `local-dev`, never production.

This plan replaces sections 4–6 of `MONEY_AGENT_CONTEXT.md`. Those sections kept splits out of MCP and made every agent write wait for approval. The owner has since decided that agents get full control, following the app's rules, with every change logged and undoable.

---

## 1. What went wrong in the first test session

The "Money MCP Testing" session failed for these reasons. Each one maps to a fix below.

| Problem | Fix |
|---|---|
| Names, handles and notes were redacted, so the agent couldn't tell who a payment was to | No redaction in the MCP view (§3) |
| No splits, shares, settlements, people, net events or owed expenses were exposed | Full model in reads, SQL and writes (§4, §5) |
| Tools defaulted to one month, and that month was empty | `get_overview` first, any month or all time everywhere (§4) |
| `owed_self` read only `owed_expense`, so July showed ₹0, and the field docs didn't say so | Field descriptions say exactly what each number counts (§7) |
| Uncategorized count was 22 in one tool and 23 in another | One definition, shared by every tool (§7) |
| The agent ran inside the repo and nearly reached for a DB script that would have hit prod | Self-contained server instructions, plus "never bypass the MCP" (§6) |

## 2. Decisions

| Topic | Decision |
|---|---|
| Query layer | Purpose-built tools **plus** read-only SQL over a curated Money model, reusing Ask Money's SQLite sandbox |
| Redaction | None for the account's own data. Agents see names, handles, raw descriptions, notes, splits, settlements |
| People ↔ payees | Learn links from past settlements and similar handles, then the owner confirms once |
| New statement | Agent saves the **sure** suggestions itself (logged, undoable) and asks about the rest, grouped by payee |
| Split a bill | One matching payment: use it and say which. Several: always ask. Close but not exact name: always ask |
| Settle up | A person's money goes to their shares oldest first, with partials. The agent reports what it covered. It asks only when the owner named a bill that breaks that order |
| Month review | "Missed" = uncategorized rows, unpaid split shares, unlinked money from known people, repeated amounts with no explanation |
| Statement import by agents | Parked. Upload stays in the app |
| Later | Duplicates, stopped subscriptions, narrate-before-upload (Flow D) |

"Sure" for a category means one of:
- the payee has a default category,
- two or more earlier payments to the same payee share one category, or
- the owner's note names a category.

## 3. What the agent sees

Everything in the owner's own account:
- dates and amounts
- payee display names, UPI handles and raw bank descriptions
- notes and categories
- people, splits, shares, settlements, net events and owed expenses
- standing notes, rules and payee defaults

Still hidden:
- database ids (refs stand in for them, as today)
- tokens and password hashes
- ChatGPT connection data
- any other user's data

Consequences in code:
- `src/lib/mcp/view.ts` stops calling `modelSafePayee` / `modelSafeText` for MCP output.
- The `note_hidden` rule (`noteHiddenFromAgent` in `src/lib/ledger/rules.ts`, the check in `transaction-fields.ts` and `undo.ts`) is removed, because no note is hidden any more.
- **Ask Money is unchanged.** It sends data to ChatGPT, so its redaction stays until the owner decides otherwise.

The bank cuts the owner's UPI remarks down to 1–4 letters ("U", "Pa", "Petr"). `parsed_purpose` is shown, but the descriptions tell the agent not to read meaning into it.

## 4. Tools

### Read

| Tool | What it answers |
|---|---|
| `get_overview` | Months imported, date range, per-month counts (rows, uncategorized, unsplit, open shares), all-time totals, people with open balances. **Call first.** |
| `list_transactions` | Filters: any month, a date range, or all time; payee, person, category, amount range, direction, note text, uncategorized, has split, has open share. Paged with a cursor |
| `get_transactions` | Full detail for refs: split, shares, settlements, net event, linked person, change history |
| `find_payments` | Ranked candidates for "the ₹567 on 31 Jul at Rooster X" or "₹100 from Kiran last week", each with a reason (amount, date distance, payee, person link) |
| `list_people` | People, their linked payees/handles, suggested links not yet confirmed, open balance |
| `get_open_balances` | Per person: each open share and owed expense, oldest first, with the date, what it was and the amount left |
| `list_payees` | Counterparties with handle, display name, default category, linked person, row count |
| `get_period_summary` | Same as today, with exact field descriptions (§7) and any range, including all time |
| `query` / `describe_table` | Read-only SQL over the curated model (§5) |
| `list_categories`, `list_standing_notes`, `list_changes` | As today |

### Write (scope `write`)

Every write goes through a ledger core with the existing guarantees:
- row locks
- `rev` stale guards
- all-or-nothing
- `ledger_change` log
- idempotency key
- server-side undo

| Tool | Notes |
|---|---|
| `update_transactions` | As today (category, note, transfer flag, review flag) |
| `set_payee_default` | As today |
| `rename_payee` | Set a counterparty's display name |
| `link_person` | Confirm a payee ↔ person link (from a suggestion or the owner's words) |
| `create_split` / `delete_split` | Participants must be existing people or names the owner wrote. Shares in paise, remainder to the owner. Delete is refused if anything is settled |
| `record_settlement` / `clear_settlement` | Link an inflow to shares, oldest first by default, with partials |
| `net_settle` | Same rules as the app's net settlement |
| `add_owed_expense` | Money the owner owes someone |
| `add_standing_note` | Lasting rules the owner states ("Rooster X is always food") |
| `undo_change` | As today |

Split, settlement, net-event and owed-expense writes are server actions today (`split-actions.ts`, `net-event-actions.ts`, `reimbursements/*`). They move into `src/lib/ledger/` cores first, so the app and agents call the same code. That is the same "one core, two doors" pattern used for transaction fields.

Not agent tools: importing statements, editing a row's amount, date or account, deleting transactions, tokens, AI settings, migrations.

## 5. Query layer

`query` runs SQL in the existing sandbox (`src/lib/assistant/query-sandbox.ts`): an in-memory SQLite copy, a separate locked-down process, read-only, with a 100-row cap.

The MCP gets its own table set, alongside Ask Money's `QUERY_TABLES`. It is unredacted, and refs stand in for ids:

| Table | Rows |
|---|---|
| `transactions` | ref, date, amount, direction, payee, handle, raw_description, purpose, note, category, is_transfer, needs_review |
| `payees` | payee, handle, kind, display_name, default_category, person |
| `people` | name, open balance |
| `splits` | transaction ref, total, your_share |
| `shares` | split ref, person, expected, settled, left |
| `settlements` | inflow ref, share or owed expense, amount, date |
| `net_events` | person, inflow/outflow refs, amount |
| `owed` | person, date, what, amount, settled |
| `categories`, `standing_notes` | |

Money columns come back in rupees, as in Ask Money.

Rule for the agent: use a purpose-built tool when one fits, and SQL for questions no tool answers. A ref found by SQL can be written to like any other ref.

## 6. Self-contained instructions

Everything the agent needs to know arrives in the MCP server's `instructions` and tool descriptions. It should not need this repo, `AGENTS.md`, or the machine it runs on. The instructions say:

1. Start with `get_overview`. Never assume a month. Look across months or all time when the question needs it.
2. Amounts are exact rupee strings. Never do money math in your head. Use tool results.
3. People and payees: a person can have several handles (Kiran has four). Use `list_people` links. Treat a suggested link as a guess until it's confirmed.
4. Before a write, read current refs and revs. Use a fresh idempotency key per request.
5. Follow the playbook rules in §8: when to act and when to ask.
6. After writing, tell the owner what changed and the change id they can undo.
7. **Never bypass the MCP.** No DB scripts, no app internals, no `.env` files. If a tool is missing, say so.

## 7. Fixes to existing reads

- `get_period_summary`: every field says what it counts. `owed_self` = owed expenses only. `others_share` = other people's split shares. Add `open_shares` = what people still owe on that period's splits.
- One shared definition of uncategorized, used by summary, overview, filters and SQL. This fixes the 22 vs 23 mismatch.
- Default range = all time when none is given, with paging. Not "the latest month".

## 8. Playbooks

Real data from `local-dev`, copied from production. Each playbook shows the tools called and where the agent stops to ask.

### 8.1 "Kiran owes me 274"
1. `find_payments(amount 274 as a share, person Kiran)` → the 31 Jul ₹567 Rooster X payment. Split: total ₹567, your share ₹293, Kiran ₹274, unsettled.
2. Reply: "That's the Rooster X bill on 31 Jul. Kiran's ₹274 share is still open. He owes ₹582 in total across 6 shares." No write needed.

### 8.2 New statement
1. `get_overview` → the new month: 61 rows, 26 uncategorized.
2. The sure rows (payee default, two or more earlier same-category payments, or a note naming a category) are saved with one `update_transactions`, and the change id is reported.
3. The rest are asked about grouped by payee, biggest group first. Answers become categories, plus a payee default when the owner says "always".
4. Inflows from linked people are matched to open shares (8.4).

### 8.3 Split a bill: "Split the Rooster X one with Kiran, equally"
1. `find_payments` → one match, 31 Jul ₹567. The agent uses it and names it in the reply.
2. Several matches → list them and ask. "Ravi" when the people are "Ravi Teja" and others → ask.
3. This payment is already split (₹293 yours, ₹274 Kiran), so the agent says so and asks before replacing it. On an unsplit payment it calls `create_split` → ₹283.50 / ₹283.50 (odd paise go to the owner) and reports the change id.

### 8.4 Settle up: "Kiran paid me back"
1. `get_open_balances(Kiran)` → ₹6 (20 Apr), ₹36.67, ₹58.33, ₹67 (13 May), ₹140 (17 Jun), ₹274 (31 Jul) = ₹582.
2. Unlinked inflows from Kiran's handles: ₹100 on 27 Jul and ₹55 on 3 Aug.
3. Oldest first: ₹100 clears ₹6 and ₹36.67 and puts ₹57.33 towards the ₹58.33 dosa. ₹55 clears the last ₹1 of the dosa and puts ₹54 towards the ₹67 Softy. The agent records both and reports: "₹427 still open: ₹13 Softy, ₹140 rackets, ₹274 Rooster X."
4. If the owner said "the 100 was for the rackets", the agent asks before breaking oldest-first order.

### 8.5 Month review: "What did I miss in August?"
Returns four lists, each with refs:
- uncategorized rows (26)
- open split shares
- money from known people with no settlement
- repeated amounts with no note or category (for example ₹272.58 four times between 25 Jul and 6 Aug)

The agent offers to fix each list, one list at a time.

## 9. Schema

- **People ↔ payees** needs one additive migration (`0015`): a nullable `counterparty.person_id` (or a `person_payee` table if a payee can belong to several people). Suggested links are computed on read, not stored.
- Nothing else is new. Splits, settlements, net events and owed expenses already have tables, and `ledger_change` (0014) logs everything.
- `0014` and `0015` run on `local-dev` only. Production migrations wait for the owner's explicit go-ahead.

## 10. Build order

Each phase is a commit on a `cursor/` branch, with draft PRs only. Each is tested against `local-dev` with a real agent running the playbooks above.

1. **Open the view.** Remove MCP redaction and `note_hidden`. Add exact field descriptions, one uncategorized definition, all-time ranges, and the new server instructions. Add `get_overview`.
2. **Read the whole model.** `get_transactions` with splits and settlements, `list_people`, `list_payees`, `get_open_balances`, `find_payments`, and MCP `query` / `describe_table` with the §5 tables. Playbooks 8.1 and 8.5 (read part) should pass.
3. **Split and settle cores.** Move split, settlement, net-event and owed-expense writes into `src/lib/ledger/` with logging and undo. App actions call the cores, and app behavior doesn't change. DB tests cover each core and its undo.
4. **Write tools.** `create_split`, `delete_split`, `record_settlement`, `clear_settlement`, `net_settle`, `add_owed_expense`, `rename_payee`, `add_standing_note`. Playbooks 8.3 and 8.4 should pass.
5. **People links.** Migration `0015`, link suggestions, and `link_person`. Playbook 8.2 should pass end to end.

**Done** means:
- a fresh agent with only the MCP URL and token (no repo) runs all five playbooks on `local-dev`
- every write shows in Recent changes and undoes cleanly
- unit tests, DB tests, typecheck and preflight all pass
